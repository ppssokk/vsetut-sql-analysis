# ВсёТут: витрина клиентских данных и SQL-анализ

Проект посвящён подготовке клиентской витрины маркетплейса и анализу покупательской активности с помощью **SQL и PostgreSQL**. Он выполнен в рамках курса Яндекс Практикума по учебному техническому заданию, на предоставленных данных и с ревью.

## Задача

Подготовить агрегированные характеристики клиентов для продуктовой аналитики и возможного дальнейшего использования в моделях машинного обучения. Исследование ограничено тремя регионами с наибольшим числом доставленных и отменённых заказов. Одна строка витрины соответствует сочетанию **клиент — регион**: клиент, делавший заказы в нескольких подходящих регионах, может присутствовать несколько раз.

После подготовки витрины выполнены четыре ad hoc исследования: сегментация клиентов по числу заказов, ранжирование по среднему чеку, сравнение регионов и анализ групп по месяцу первого заказа в 2023 году.

## Подготовка витрины

Запрос объединяет данные схемы `ds_ecom` из таблиц `users`, `orders`, `order_reviews`, `order_items` и `order_payments`. Сначала позиции, оценки и платежи агрегируются на уровне заказа, затем собираются характеристики клиента в регионе. Это позволяет учитывать данные из таблиц с несколькими строками на заказ без прямого перемножения этих строк при соединении.

В витрине рассчитываются:

- даты первого и последнего заказа и интервал между ними;
- количество заказов, оценок и отмен, средняя оценка и доля отмен;
- суммарная и средняя стоимость доставленных заказов;
- количество заказов с рассрочкой и промокодом, признаки использования рассрочки, денежного перевода и отмены.

Оценки, представленные в исходных данных по шкале 10–50, приводятся к шкале 1–5. Стоимость заказа рассчитывается как сумма цены товаров и доставки.

## Анализ и выводы

Результаты приведены по комментариям к запросам автора; учебная база данных в репозиторий не входит.

1. **Сегментация.** Большинство клиентов в исследуемой витрине совершили один заказ. Группы с 6–10 и 11+ заказами малочисленны, поэтому их средний чек не следует обобщать без дополнительного исследования.
2. **Ранжирование.** Среди 15 записей с наибольшим средним чеком при трёх и более заказах средний чек составлял примерно 5,5–14,7 тыс. руб. Большинство клиентов этой группы совершили по три заказа.
3. **Регионы.** По комментариям к результатам, Москва лидировала по объёму: около 39,4 тыс. клиентов и 40,7 тыс. заказов. Среднее значение клиентского среднего чека было выше в Санкт-Петербурге; промокоды использовались относительно редко.
4. **Группы по месяцу первого заказа.** В 2023 году число новых клиентов в целом росло к концу года. Для более поздних групп доступен более короткий период наблюдения, что важно учитывать при сравнении длительности активности.

В региональном и помесячном запросах средний чек считается как **среднее клиентских средних чеков**, а не средневзвешенная стоимость всех заказов. Витрина имеет детализацию «клиент — регион», поэтому её строки нельзя автоматически трактовать как уникальных клиентов во всей выборке.

## SQL-приёмы

CTE, `JOIN` и `LEFT JOIN`, агрегация на разных уровнях детализации, `FILTER`, `CASE`, `BOOL_OR`, `ARRAY_AGG` с сортировкой, `DENSE_RANK`, `NULLIF`, работа с датами и интервалами.

## Файлы и запуск

```text
├── analysis.sql   # Запрос витрины, четыре ad hoc запроса и комментарии к результатам
└── README.md      # Описание задачи, логики и результатов
```

Для воспроизведения нужен PostgreSQL с учебной схемой `ds_ecom` и исходными таблицами. Исходные данные и DDL этих таблиц в репозиторий не входят.

Первая часть `analysis.sql` — **SELECT-запрос, формирующий витрину**, а не команда создания таблицы. Четыре последующих запроса обращаются к `ds_ecom.product_user_features`. Чтобы запустить их на новой базе с нужными исходными данными, сначала нужно сохранить результат первого SELECT в эту таблицу, например с помощью `CREATE TABLE ds_ecom.product_user_features AS ...`, и убедиться, что у пользователя есть права на её создание. Не запускайте эту команду поверх существующей таблицы без предварительной проверки.

Последний запрос использует `SET lc_time = 'ru_RU'` для названий месяцев; доступность этой локали зависит от сервера PostgreSQL. Без исходной базы результаты воспроизвести невозможно.
